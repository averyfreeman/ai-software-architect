**1\. Security: a command intended to read files can end up running project code**

The existing [command safety check](https://github.com/leomuf/ai-software-architect/blob/8ad080b314403c148c7b53ff12acf44545071d17/adapters/codex/control_plane.py#L358-L401) checks the text of a command before the terminal processes it. The terminal can then change what the command means.

For example, `rg needle *` looks like a normal file search. In Bash, `*` is replaced with the names of files in the folder. A specially named file, such as `--pre=sh`, can then be treated as an instruction to run another program instead of as a filename. Project content can therefore run when the plugin intended only to read it.

This was reproduced with Git Bash on Windows using a test file that only creates a harmless marker. This is an existing weakness, so it was not introduced by your changes. It is relevant to Windows when using Git Bash and to the shell behavior needed for macOS and future Linux support. The same test has not yet been run on macOS. This affects the plugin's own read-only protection; it does not bypass Codex's separate sandbox.

**Two options for addressing this shared issue**

Because this weakness already exists in the project, we do not expect you to take responsibility for it just because you are adding macOS support. Please choose whichever option works best for you:

1. **Fix it in this PR.** If you would like to address it now alongside the other PR issues, please implement a shared solution for Windows and macOS that can also support Linux later. The approach below is our suggested starting point. Include tests showing that normal inspection still works and the unsafe command is blocked.
2. **Leave the security fix to us.** You can focus on the issues introduced by this PR, especially the Windows type-check and test failures. Once those are resolved and the Windows and macOS automated checks pass, we can merge the platform-support changes. We will then implement and test the shared security fix in a separate PR **before publishing the next release**. Choosing this option will not, by itself, block the merge.

Please let us know which option you prefer. In either case, the security fix must be completed before the next release reaches users. The checksum publication issue and the real macOS installation checks must also be completed before that release.

**Suggested solution for whoever implements the fix**

We recommend using the bundled repository reader as the common route for shell-based project inspection, instead of trying to decide whether arbitrary terminal commands are safe.

1. In the active architecture workflow, allow only the exact command generated by `repository_snapshot_command` to start the bundled reader. Remove the general exceptions for commands such as `rg`, `git`, and PowerShell reads from this shell-command gate. Keep safe, separately controlled file-reading tools available.
2. The bundled reader should inspect files using Python file APIs, with the existing path, size, and sensitive-file checks. It must not run, import, or build code from the project being inspected.
3. If the reader needs an extra capability, such as a targeted text search, add a small, validated operation to that reader. Do not fall back to a model-written shell command. Keep its implementation shared across platforms; only the launcher should need platform-specific quoting.
4. Reject changes to the trusted launch command, including extra arguments or a second command. Check any tool options that can select another shell or interpreter, so the same command is not accepted under an unexpected interpretation. Update the workflow instructions to use this restricted route.
5. Add tests that pass through the actual PreToolUse hook. Include the specially named file, quoted paths, paths containing spaces or apostrophes, and attempts to append another command. Check that normal inspection succeeds and the marker file is never created. Run these tests with PowerShell and Git Bash on Windows, the supported shell on macOS, and Bash on Linux before Linux is advertised as supported.

This gives the platforms one shared inspection policy and avoids relying on a growing list of dangerous shell expressions.

**2\. The Windows type check now fails**

Mypy is the tool that checks whether Python values are used with the expected types. Eight new comments telling it to ignore an error are unnecessary on Windows, and the project's strict settings treat those unnecessary comments as errors.

Please make the Windows-only API access explicit and run the type check on both Windows and macOS. The inline comment lists the affected locations and a proposed approach.

**3\. Three new tests fail on Windows**

One test expects macOS-style file paths even when it runs on Windows. Two tests assume Windows supports the same executable permission bits as macOS.

Please keep the actual macOS path and permission checks on a macOS test runner, add or retain equivalent Windows checks, and keep tests that do not depend on the operating system running on both. The inline comments explain the changes in more detail.

**4\. The checksum files conflict when publishing both downloads**

A checksum is a file fingerprint that users can compare to check their download. Both platform builds create a different file named `SHA256SUMS.txt`. A single GitHub Release cannot attach both files under that same name.

Please add a final packaging step that collects both ZIPs and creates one checksum file listing both downloads. The inline comment describes how to test this.

**4\. Both downloads need to be listed in the release checksum file**

A checksum is a fingerprint of a download. Users compare it to check that the downloaded file matches the released file.

This code writes one file named `SHA256SUMS.txt`, containing only the macOS ZIP's checksum. The Windows packaging script creates another file with the same name, containing only the Windows ZIP's checksum.

The two build jobs can store these files separately, but a single GitHub Release cannot attach both under the same name. Copying one over the other also loses the checksum for one platform.

**Proposed fix**

1. Keep the Windows and macOS build outputs separate until both jobs finish.
2. Add a final job, dependent on both successful builds, that downloads the two ZIPs and calculates their SHA-256 checksums.
3. Write one `SHA256SUMS.txt` containing two lines: one checksum and exact ZIP filename per platform. Make that combined file available with both ZIPs for publication.
4. Update the release guide to tell the maintainer to publish the combined file.
5. Add a test that checks both filenames are present and each checksum matches its ZIP. Adding another supported platform later should add another line rather than overwrite existing entries.

If a combined job is outside this PR's scope, an alternative is to give each checksum file a platform-specific name and update both the installation instructions and release guide accordingly. Please choose and document one complete approach.
